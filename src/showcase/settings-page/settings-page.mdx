# Settings page

Sections on the left, one form on the right, and a save bar that appears only
when there is something to save. The hard part is deciding what happens to
unsaved work when someone switches section or closes the tab.

## Try it

Change any field and the save bar slides in at the bottom. Save or discard and
it disappears.

## The layout skeleton

A two column grid inside a column flex page, so the save bar can sit outside the
scrolling area:

```scss
.page { display: flex; flex-direction: column; height: 680px; }

.page__body {
  flex: 1;
  min-height: 0;          // lets the children scroll instead of the page
  display: grid;
  grid-template-columns: 240px 1fr;
  gap: 24px;
  overflow: hidden;
}

.content { overflow: auto; min-height: 0; }
```

The nav and the content scroll independently. The save bar is a sibling of the
grid, so it stays pinned however long the form gets.

On a phone the same markup switches to one column and the nav becomes a
horizontal strip:

## One form, many sections

Every section renders from a single `FormGroup`. `@switch` swaps which fields
are on screen, but the form object never changes:

```ts
readonly form = this.fb.nonNullable.group({
  name: ['', [Validators.required]],
  emailDigest: [true],
  scheme: ['system'],
  // ...every section's controls
});
```

```html
@switch (active()) {
  @case ('profile') { <!-- name, email, bio --> }
  @case ('notifications') { <!-- toggles and digest day --> }
}
```

This choice makes the save bar possible. One form means one `dirty` flag and one
save call, so switching sections never loses what someone typed. With one form
per section you need per-section dirty tracking, a confirm dialog on every
section change, and a save button that saves only part of the screen.

The trade off: controls in hidden sections still exist and still validate. If
section four has a required field, the save button stays disabled while the user
looks at section one wondering why. Keep required fields off optional sections,
or show which section holds the error.

## The save bar

```ts
private readonly status = toSignal(this.form.events, { initialValue: null });

readonly dirty = computed(() => {
  this.status();          // re-run whenever the form emits
  return this.form.dirty;
});
```

`form.dirty` is a plain property, not a signal, so a `computed` that reads it
will not re-evaluate on its own. Subscribing to `form.events` gives the computed
something to depend on. In a zoneless app, without it the save bar never
appears.

`discard()` resets to the current raw value and marks the form pristine, which
clears the bar without wiping what the server last sent.

## Toggles versus checkboxes

<Example of={SettingsStories.NotificationsSection} />

Use `mat-slide-toggle` when the change takes effect immediately and means on or
off. Use `mat-checkbox` when the value is part of a form you submit, or when it
is one of several in a list. This screen uses both: the notification switches
read as settings, and "Reduce motion" reads as one option among several.

## Destructive actions

<Example of={SettingsStories.SecuritySection} />

The delete action sits at the bottom, in its own bordered block using the error
role, away from everything else. The rules:

- Never put a destructive button next to a save button.
- Colour it with `--mat-sys-error-container` and `--mat-sys-on-error-container`, not a hardcoded red.
- Confirm it with a [dialog](?path=/docs/popups-and-modals-dialog--docs) that names the thing being deleted.

## API you will use

| Member | Type | What it does |
| --- | --- | --- |
| `mat-nav-list` with `a mat-list-item` | `[activated]` | Section navigation. `activated` sets `aria-current="page"` on anchors. |
| `matListItemIcon` / `matListItemTitle` | content slots | The icon and label inside a list item. |
| `mat-slide-toggle` | `formControlName` | An immediate on/off setting. Works with reactive forms out of the box. |
| `mat-hint` | `align="start" \| "end"` | Helper text. `align="end"` is where character counters go. |
| `subscriptSizing` | `'fixed' \| 'dynamic'` | `fixed` reserves a line for errors so the layout never jumps. Default and usually right on a settings form. |
| `form.events` | `Observable<ControlEvent>` | The stream to feed `toSignal` when you need `dirty`, `touched` or `status` in a computed. |
| `form.markAsPristine()` | method | Call after a successful save so the save bar goes away. |

## Accessibility

- The section list is a `<nav aria-label="Settings sections">`. Without the label, a screen reader announces "navigation" and nothing says which one.
- `[activated]` on an anchor list item emits `aria-current="page"`, so the current section is announced as well as highlighted.
- Every field has a `mat-label`. A placeholder is not a label: it disappears once someone types.
- The save bar is a `<footer>` with visible text, not an icon-only toast. It has to be readable by someone who did not see it animate in.
- The destructive block states the consequence in text ("This cannot be undone"), not by colour alone.

## Common mistakes

1. **Reading `form.dirty` inside a `computed` with nothing to depend on.** It never re-evaluates. Feed the computed from `form.events`.
2. **A save button that is always enabled.** People click it out of habit and cannot tell whether anything happened. Show the bar only when the form is dirty.
3. **One form per section.** Every section change then needs its own confirm-or-lose prompt.
4. **Losing input when the section changes.** If the controls are destroyed with their values, `@switch` is hiding a bug. Keep one form group.
5. **A delete button beside save.** Separate it, colour it with the error role, and confirm it.
